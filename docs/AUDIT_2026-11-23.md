# 代码审查记录（2026-11-23）

本轮对 `y901` 做了一轮"读源码找真 bug"的审查，范围集中在
`y901-ui`（布局/脏区/绘制遍历）、`y901-widgets`（新加的 `TextArea` 与既有控件）、
`y901-render`（软光栅、字形引擎、图集）。

**原则**：每条发现都必须能给出 `file:line` + 可触发输入；修复必须带回归测试，
并且**验证过测试能抓到旧 bug**（把修复临时撤掉，测试要红）。没有证据的"感觉可能有问题"不写进来。

## 第二轮：把第一轮"不敢动"的三项也修掉了

第一轮有三项被列进"已知但未修"，理由是"改动面大、怕引出新问题"。第二轮用
可验证的方式把它们做掉了 —— 每项都有新回归测试，且**都做过变异验证**。

### A. 百分比尺寸在 measure / arrange 之间不一致（原 F2）

问题：`measure` 按"父级给的可用空间"解析百分比，`arrange` 按容器**实际 rect** 重算。
容器尺寸一旦是内容驱动的（自动高度 + `Align::Center`），两处就会分歧 ——
量出 100 高的列，子项摆进去只有 50 高，列里留 50px 空洞。

修法：**让测量结果成为唯一事实**。`flex_measure_into` 的 `measured` 快照不再存
"控件自报尺寸"，改存**该子项最终会被分配的尺寸**（已含 `Px` 缩放、百分比解析、
min/max 钳制）；`flex_arrange_with` 一律消费它，不再二次解析。
`Align::Stretch` 与显式交叉轴尺寸的优先级（显式优先）保持不变。

测试：`crates/y901-ui/tests/layout_percent.rs`
- `percent_child_never_exceeds_its_auto_sized_container`
- `percent_child_fills_a_stretched_container`（有界时仍是 50% = 100，保证没改坏原有语义）

变异验证：把 `measured.push` 改回存自报尺寸，两条测试立刻变红
（`g.h=4 c.h=100` / `实际 4`）。

### B. `cache_key()` 与 `id_key(id)` 的键空间分裂（原 F4）

问题：`measure`/索引表用 `cache_key()`，而 `rect_of`/`invalidate`/`mark_dirty` 用
`id_key(id)`。第三方控件一旦返回非 id 派生键，两边指向不同的桶 ——
表现为"某些节点永远不刷新"，而且**完全没有报错**。

修法：新增唯一入口 `layout::key_of(node)`（`cache_key()` 优先、否则 `id_key`），
所有读键的地方统一走它；并在调试构建里用 `debug_assert_eq!` 把契约变成**硬约束**：
`cache_key()` 只能当 `id_key(id())` 的预算缓存，不能当自定义键。

测试：`crates/y901-ui/tests/layout_robustness.rs::custom_cache_key_is_rejected_loudly`
（违反契约会 panic，消息里带 `cache_key`）。

### C. 布局中途 panic 会永久丢掉 rect 索引（原 F3）

问题：`layout()` 曾用 `mem::take` 把 `rects` 搬到局部变量。控件在 `measure`/`arrange`
里 panic（三方控件常见）时，表就永久空着：`rect_of()` 全为 `None`、
`invalidate(id)` 静默 no-op、下一轮还把整棵树当"全新节点"（于是没有旧∪新标脏 → 残影）。

修法：布局期间**不动** `rects`；末尾用**备用缓冲 `spare`** 与它交换（零分配），
对比完再把缓冲还回去。另在 `layout_tree` 入口清空 `cache.stack` ——
panic 会跳过 `measure` 里的 `pop`，残留的祖先链会让下一轮 `parents` 写错。

测试：`layout_robustness.rs` 的 `rect_of_survives_a_panicking_layout`（用
`catch_unwind` 真的制造 panic）、`layout_recovers_after_a_panic`。

变异验证：把布局前 `self.rects` 清空（旧行为），第一条立刻报
`left: None / right: Some(Rect { .. w: 10.0 .. })`。

### D. 弹出层不在 rect 索引里（原"契约瑕疵"）

问题：`rect_of(id)` 与 `invalidate(id)` 都查索引表，而索引表只走 `self.root`，
浮层子树（树外）一个都不在里面。后果不是"少个便利"而是**功能性缺陷**：
对浮层里的控件 `invalidate(id)` 会**静默 no-op** —— 局部重绘下它永远不刷新，
只能靠无关的整窗重绘偶然救回来；`rect_of` 也查不到（自动化/测试拿不到几何）。

修法：布局末尾（**无论是否走了跳过快路径**）把浮层子树的 rect 补进索引表。
只进 `rects`、**不进 `paint_order`** —— 命中测试与路径重建依赖树路径，
浮层路径不在树里，混进去会让 `hit_index`/`path_of` 对不上号。
另外浮层被**重新摆放**时（锚点移动、滚动、窗口缩放）现在会 `旧∪新` 标脏：
浮层不在树里，`mark_moved_map` 看不到它的位移，旧位置会留残影。

测试：`crates/y901-ui/tests/popup_index.rs`（2 条）。

### E. `render::atlas::Atlas` 的两个缺陷（原"只被自身测试使用，不值得修"）

虽然生产路径走 `MyFontEngine` 自己的 packer，但这个模块是 `pub` 的，
两个缺陷都是"数据错位"级别：

1. `place()` 命中缓存时**不比对新请求的 w/h**。同一个 `GlyphKey` 被要求更大尺寸时
   （换字号/回退字体），返回旧尺寸的槽，调用方按新尺寸的 `src` 交给 `write`，
   而 `write` 按 `slot.w` 逐行拷贝 —— **行对不齐的花屏**。现在尺寸不符按未命中处理。
2. `compact()` 里插入失败的条目 `continue`（注释说"保留原槽位"），但 `self.data`
   已被整张新图集替换、且中途被别的条目覆盖过 —— 那条记录之后的坐标指向**别人的像素**。
   现在重建槽表（失败的丢弃，下次按需重画）。

测试：`atlas::tests::place_reallocates_when_the_requested_size_changes`（变异验证：
把尺寸比对去掉，立刻变红）。

### F. shaping 路径其实**从未真正跑过**（本轮最意外的发现）

原以为只剩"混排 run 拆分"这一个已知缺口，动手时才发现更底层的问题：
`impl FontEngine for MyFontEngine` 里**没有转发** `font_data` / `font_data_for` /
`face_for` / `glyph_keyed` / `glyph_keyed_at`。这些方法只以**固有方法**存在于
`MyFontEngine` 上，而 `SoftBackend` 持有的是 `Box<dyn FontEngine>` —— 调用落到
trait 默认实现，`font_data()` 默认返回 `None`，于是 `font_data_for(0)` 也是 `None`，
`draw_text_shaped` 一检测到"没有字体字节"就整体退回 cell 路径。

**结论：阿拉伯/希伯来/印度语系/组合记号在多行文本之外，全部静默走 cell 路径**
（也就是拿等宽格逐字符画，不做连写、不做 bidi）。这使得前面那条"shaped 文本按
`px_final` 取位图"的修复也成了死代码。

修法：在 trait impl 里补齐转发。接通之后 shaped 路径才真正被测试覆盖。

### G. 混排双向文本会重叠（接通 shaping 后才暴露）

`draw_text_shaped` 先按**字体面**切段（不是按 Bidi run），再用"负 pen + 事后整体平移"
模拟 RTL 对齐。`"hello שלום"` 全在同一个字体面里 → 只有一段，希伯来段被当拉丁段排；
一旦真的切成多段，RTL 段拿到 `rtl_base = pen`，`place_run` 会把它翻到 `pen - width`
（英文**前面**）—— 与英文重叠。

修法：
1. 新增 `text::bidi::visual_runs_of`（`unicode_bidi::visual_runs` 的薄封装），
   返回**已按视觉顺序排列**的 `(字节区间, 是否 RTL)`；
2. `draw_text_shaped` 改成**两级切分**：先按 Bidi 视觉 run、再在每个 run 内按字体面切；
3. 摆放改成**两遍**：先全部 shape（拿到每段宽度），再按视觉顺序逐段摆放，
   RTL 段传"该段右边界"。

测试：`crates/y901-render/tests/shaped_bidi_placement.rs`（4 条）。
变异验证：把 `base` 改回 `pen`（不给 RTL 段右边界），
`mixed_direction_runs_do_not_overlap` 立刻报
"混排最右像素 77，拉丁段末端 80，希伯来段宽度约 34"。

## 仍未修（附理由）

| 项 | 为什么不修 |
|---|---|
| bidi 的**段内**多方向（一个字体面内既 LTR 又 RTL 的连续 run）目前由 shaper 单方向处理 | 要彻底正确需要把 run 拆分做到"每段单方向 + 单字体面"的笛卡尔积，并把 cluster 映射与光标/选区一起改；工作量与风险都远超本轮"审查修复"，已在 shaped 路径的注释里标明现状。 |
