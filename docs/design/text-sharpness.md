# 文字清晰度：成因、实测与守卫

> 结论先行：**"字体糊"的主因是字形四边形落在分数像素上被线性采样重采样**，
> 已在 `c60a923` 修复（字形落点吸附整像素 + 行级基线取整）。
> 本文记录的是判断依据、可复现的度量方法，以及**为什么没有把它写成像素比值断言**。

## 1. 机制

图集位图是 **1:1 贴到屏幕**上的（四边形尺寸就是位图的 `width x height`），
采样器却是 `D3D11_FILTER_MIN_MAG_MIP_LINEAR`。

像素中心在 `x + 0.5`。当四边形左上角 `X` 是整数时，每个像素中心正好落在
**纹素中心**上，线性采样退化为"取该纹素"，输出与位图逐字节相同；
只要 `X` 带小数 `f`，采样点就落在纹素内部，相邻纹素按权重混一次 ——
笔画被摊到 2~3 个像素，峰值亮度掉到六成。

分数位置的来源有两个，都真实存在过：

| 来源 | 何时出现 | 例子 |
|---|---|---|
| `map_pos()` 乘 DPI 缩放后不取整 | 125% 缩放 | 逻辑 `x=53` → 物理 `66.25` |
| 行级基线 `origin_y + ascent` 本身是小数 | **任何缩放** | 16 号字 `ascent = 13.75` |

## 2. 实测（修复前 → 修复后）

同一段文字、同一台机器，取竖笔横截面（亮度，正文字色 244）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 100% 缩放，`1` 的竖笔 | `21 \| 169 167 \| 21`（两个像素等值 = 位图原样） | 峰值到 255 |
| 125% 缩放，`1` 的竖笔 | `21 \| 74 143 90 \| 21`（摊成三个像素，峰值 57%） | 两步到底 |
| 整窗亮部像素（≥200） | 1617 | 1825（+13%） |
| 边缘梯度均值 / p95（1.25 缩放离线回读） | 14.92 / 77.3 | 16.82 / 87.2（+12.8%） |

## 3. gamma 校正 A/B（`Y901_GAMMA_AB=1`）

`ps_main` 里对 ClearType 覆盖率做了 `pow(cov, 1/2.2)`（`padding.x` 传入，
默认 1/2.2）。自检开关会把同一帧分别按 `gamma=1.0` 与 `1/2.2` 画一遍并打印统计：

| gamma | mean_luma | bright（占比） |
|---|---|---|
| 1.0000 | 0.0325 | 1.00% |
| 0.4545 | 0.0344（**+5.8%**） | 1.26%（**+26%**） |

即：gamma 校正把整体亮度抬了约 6%、把"亮像素"数量抬了约 26%——
观感上就是笔画更粗、更"奶"。它当初是为了消除"发灰"，属于**风格取舍**而非正确性，
所以本轮**保持默认不动**，只保留 `Y901_GAMMA` 环境变量做 A/B。

## 4. 与 GDI 的对比（解释"为什么还是不如系统记事本锐"）

用 `System.Drawing` 以同一字体（NSimSun）、同一像素字号（16px）画同一串文字，
`TextRenderingHint` 取 `AntiAliasGridFit` / `ClearTypeGridFit` 两种，结果**都只有
1 种灰度（全 255）** —— GDI 在这个字号用的是字体自带的**点阵位图（bitmap strike）**，
根本没有抗锯齿。

而我们的引擎走 DirectWrite `GetGlyphRunAnalysis` 的**轮廓 + ClearType 抗锯齿**，
在小字号上必然出现过渡像素。这是**渲染模式差异，不是 bug**：
要拿到 GDI 那种"硬边"，得改用 `DWRITE_RENDERING_MODE_GDI_CLASSIC` 或干脆用点阵位图，
属于另一个量级的改动，且会牺牲缩放自由度。

## 5. 守卫：为什么是单元测试，而不是像素比值

最初加过一条 GPU 像素用例 `glyph_edges_stay_sharp`（统计"近满亮像素占墨迹的比例"
与"中间灰占比"），用开关回退吸附实现做对照，结论是**它抓不到回归**：

- 该场景（固定窗口 + `draw_text`）在**开关两种实现下输出逐像素相同**（ink/hi/mid 完全一致）；
- 换了分数起笔点（`4.5, 6.3`）仍然一致 —— 说明渲染链路在这一场景下没有产生分数落点，
  比值变化只反映字体自身的抗锯齿量，与"是否吸附"无关。

一条**不会失败**的守卫比没有守卫更糟（它给人虚假的安全感），因此撤掉了。
真正有效的守卫是**单元测试**（`crates/y901-backend-win32/src/backend/mod.rs`
的 `glyph_geometry_tests`）：

| 用例 | 抓什么 |
|---|---|
| `fractional_baseline_snaps_to_integer_top` | 分数基线必须被吸附成整数顶部 |
| `glyph_pos_snaps_to_pixel_grid` | 字形左上角吸附到最近整像素 |
| `matches_soft_backend_baseline` | 软/硬后端对同一棵树给出同一条整数基线 |

**已验证有效性**：把 `.round()` 去掉后，这三条用例立即失败（实测 3 failed）；
恢复后 58 passed。
