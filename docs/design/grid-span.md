# Grid 跨格与显式定位：设计文档

> 状态：**设计草案**，未写代码。文中 `【待决策】` 表示需要指令发出者拍板的点。
> 现有实现参照 `crates/y901-ui/src/grid.rs`（顺序排布，`cell_of(i) = (i % cols, i / cols)`）。

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 是否需要改遍历顺序 | **不需要**。跨格只影响"每个子控件的矩形怎么算"，`measure`/`arrange` 仍是线性遍历 |
| 冲突检测怎么做 | 用**扫描线 + 每列占用位图**，O(n log n + n·rows/64)，而不是 O(单元格总数) 的占位矩阵 |
| 最大难点 | 不是冲突，是 **`Auto` 轨道的尺寸归因**：跨格控件的内在宽度无法归给单一轨道 |
| 缓存风险 | `LayoutCache` 的 freshness 判据是 `(constraints, version, dirty)` —— **跨格区间变了但约束没变时会读到过期尺寸** |
| 可复用抽象 | 区间集合（`IntervalSet`）+ 扫描线放**`y901-core`**；约束求解放 `y901-ui` |
| 待决策项 | **4 个**（见 §6） |

## 1. 问题定义

### 1.1 现状

`Grid` 是纯顺序排布：

```rust
fn cell_of(&self, index: usize) -> (usize, usize) {
    (index % cols, index / cols)
}
```

每个子控件恰好占一格，位置完全由插入顺序决定。没有"放到第几列"的能力，也没有跨格。

### 1.2 目标

每个子控件声明一个**矩形区间**：

```rust
grid.place("header", 0..3, 0..1);   // 列 [0,3)、行 [0,1)：横跨三列
grid.place("side",   0..1, 1..3);   // 竖跨两行
```

形式化：

- 子控件 `i` 的区间 `C_i = [c_i_start, c_i_end) × [r_i_start, r_i_end)`
- **合法性**：`c_start < c_end ≤ cols`，`r_start < r_end ≤ rows`，且所有 `C_i` **两两不相交**
- **完备性**（可选）：所有可见格都被某个 `C_i` 覆盖 —— 或存在"空格"概念，见 §6-①
- **稳定性**：未显式 `place` 的子控件按**剩余空格的最小行优先顺序**自动放置（与 CSS Grid 的 `grid-auto-flow: row` 同义）

### 1.3 与现有 API 的关系

现有 `with_children(vec![...])` 保持"顺序排布"语义不变（向后兼容）。
`place` 是**可选覆盖**：显式声明过的走显式位置，其余走自动流。

## 2. 常规做法 vs 创新做法

### 2.1 冲突检测

| | 常规做法 | 本设计 |
|---|---|---|
| 数据结构 | `Vec<Vec<bool>>` 占位矩阵（`cols × rows`） | **每列一条 64 位掩码** `Vec<u64>`（`rows` 位） |
| 复杂度 | O(Σ 区间面积) —— 一个跨 1000 行的控件就要写 1000 格 | O(Σ 区间宽度 × ⌈rows/64⌉) |
| 冲突判定 | 遇到 `true` 即报错 | 按列做 `mask & span_mask != 0` |

**常规做法在什么场景失败**：虚拟化列表里的 Grid 可能出现 `rows = 100_000`（滚动内容）。
占位矩阵是 `cols × 100_000` 个 `bool`，一次布局就要几十 MB 且全量清零；掩码只需要
`cols × 1563` 个 `u64`，并且**只清零被触碰的列**。

进一步：如果只做冲突检测（不做"找空位"），可以直接**按行排序后扫描线**，
O(n log n) 且 O(1) 额外空间。本设计选择掩码是因为**自动流也需要"找下一个空位"**，
而掩码天然支持 `trailing_zeros` 找空行。

### 2.2 跨格内容溢出

常规做法：裁剪到单元格。

问题：跨格的意义就是"给更多空间"，裁剪到单元格等于跨格白跨。

`【待决策-①】` 三种候选，各有代价：

| 方案 | 行为 | 代价 |
|---|---|---|
| A. 裁剪到**区间并集** | 跨格控件可画出整个跨格矩形，不会溢出到别的格 | 需要 `children_clip` 返回并集矩形（见 §3.4）；与"内容比跨格区域还大"的极端情况仍会裁 |
| B. 允许溢出 | 不裁剪，按 Z 序覆盖相邻格 | 与"网格"语义冲突：覆盖关系不可预测，且脏区会跨格 |
| C. 反向撑开轨道 | 内容超限时**扩大**所跨的 Auto 轨道 | 会改变其他控件位置，需要重排（两趟布局） |

倾向 A（与现有 `children_clip` 机制一致、无重排风险），但 B 对"浮层式格子"更自然。**需要决策。**

### 2.3 自动分配剩余格

常规做法：贪心 —— 按插入顺序找第一个能放下的空位。

**常规做法在什么场景失败**：当显式控件把空间切碎时，贪心会产生**无法放入但明明有空位**的碎片。
例如 3 列网格，显式放了 `(0..1, 0..1)` 与 `(2..3, 0..1)`，剩余空位是 `(1..2, 0..1)`；
若下一个自动控件需要 2 列，贪心在 row 0 找不到连续空位就跳到 row 1，
而实际上"跨 row 0-1 的第 1 列"是可用的。

本设计的做法：**两阶段**

1. **列掩码扫描**：对每个候选行，用位运算求"连续 `span_w` 列都空"的位置（`mask` 的滑动与）；
2. **行方向坍缩**：若某控件需要 `span_h` 行，检查这些行的掩码**逐位与**后是否仍有空位。

这仍是贪心（不保证最优解），但**不会像"逐格试探"那样产生假失败**，且是 O(n · rows/64)。

`【待决策-②】` 是否需要**最优解**（例如视频墙、仪表盘这类要求"尽可能紧凑"的场景）？
若需要，必须上区间 CSP（回溯 + 剪枝），复杂度最坏 O(n!)，只能对小规模（n ≤ 50）启用。

### 2.4 与布局缓存的交互

`LayoutCache::measure` 的 freshness 判据（`layout.rs:163`）：

```rust
if self.is_fresh_by_key(key, constraints, version) { return cached_size; }
```

即 `(constraints, version, dirty)` 三者都没变才复用。

**问题**：一个子控件从 `span (1×1)` 改成 `(1×2)`，但**两格的合并尺寸恰好等于原来的单格尺寸**
（比如两列各 100px，合并后 200px ≠ 100px —— 实际上几乎总会变；但"从跨 2 列改成跨 3 列、
而第 3 列是 0 宽"这种病态情况会相等）。

**结论**：`constraints` 相等就复用是**正确**的 —— 因为控件的测量结果只依赖约束，
不依赖"我占了几个格"。**但** `Grid` 自己的 `layout_version()` 必须 bump，
否则 `Grid` 的轨道重算结果会被复用。

`【待决策-③】` `Grid::place()` 是否自动 bump `layout_version`？
倾向"是"（否则用户改了 span 却看不到变化，是更难排查的 bug），但这会让 `place` 有副作用。

## 3. 与现有架构的耦合

### 3.1 遍历顺序

**不需要改。** 现有流程：

```
measure:  resolve_tracks(内容归因) → child_rects() → 逐个 child.measure(格子约束)
arrange:  child_rects() → 逐个 child.arrange(矩形)
```

跨格只改变 `child_rects()` 里 `x/y/w/h` 的算法（从"取单格"变成"取区间并集"），
遍历仍是 `for i in 0..children.len()`。**这是本设计最重要的性质：改动面被限制在一个函数里。**

### 3.2 `Auto` 轨道的尺寸归因（真正的新问题）

现在的 `resolve_tracks` 靠闭包 `content_of(i)` 把子控件的内容尺寸归给第 `i` 条轨道。
跨格之后：

- 一个跨 3 列的控件，它的 `200px` 内在宽度应该分给这 3 列 —— **按什么比例分？**
- 分完之后还要保证 `Σ col_widths[0..3] ≥ 200`，否则跨格控件装不下。

这是 HTML 表格布局算法的经典问题。本设计采用**min/max-content 两遍法**：

1. 每个子控件测一次 `min-content`（最窄）与 `max-content`（不折行），得到两个尺寸；
2. 单格子控件直接归给它的轨道；
3. 跨格控件：把 `max-content` 按"相关轨道的当前 max-content 比例"分配，
   若分配后仍不足，则**按缺口平均补足**（与 CSS 的 `distribute extra space` 一致）。

复杂度 O(子控件数 × 平均跨度)，对 10k 节点、跨度 ≤ 3 的情况约 30k 次浮点运算。

`【待决策-④】` 两遍测量意味着**每个子控件 `measure` 被调用两次**（min 与 max）。
现有 `LayoutCache` 只能缓存一个 `(constraints → size)` 对，因此需要缓存两个约束下的结果 ——
这会让缓存条目翻倍。是否接受？（替代方案：只测一次 `max-content`，min-content 用 0 近似，
代价是 Auto 轨道可能过宽。）

### 3.3 脏区计算

一个跨格控件的尺寸变化会影响谁？

- **仅影响它自己所占区间的轨道尺寸** → 进而影响**同一轨道组**内的其它控件；
- 现有 `LayoutCache::mark_dirty` 只沿**父子链**向上传播，不横向传播。

所以跨格引入了**横向依赖**：`A` 在第 0 列、`B` 跨 0..2 列，`A` 变高会改变第 0 列轨道高，
从而改变 `B` 的矩形，而 `B` 不是 `A` 的祖先。

**结论**：`Grid` 在 `measure` 里一旦发现轨道尺寸变化，必须对**整个 Grid** 调
`cache.mark_all_dirty()`（现有接口，粒度是整棵树）或新增"只脏子树"的接口。

`Grid` 的子树通常不大（几十到几百节点），整子树失效可接受；
若将来出现"上万元素的 Grid"，需要新增 `LayoutCache::mark_subtree_dirty(root_id)`。

### 3.4 `children_clip`

现状：返回**单元格矩形**（`grid.rs` 里 `children_clip(cell_rect) -> Some(cell_rect)`）。

跨格后应返回**区间并集矩形**：

```
x = rect.x + padding.left + Σ col_widths[..c_start] + gap * c_start
w = Σ col_widths[c_start..c_end] + gap * (c_end - c_start - 1)
```

**与各方案的对应**：若 §2.2 选 A（裁剪到并集），`children_clip` 直接返回上式；
若选 B（允许溢出），`children_clip` 返回 `None`，由 `Grid` 自己的 `clip()` 兜住整体。

## 4. 验收标准

### 4.1 必测场景

| # | 场景 | 断言 |
|---|---|---|
| 1 | 单格（现有行为） | 几何完全不变（回归基准） |
| 2 | 跨列 `0..3 × 0..1` | 宽度 = 三列宽 + 两个 gap |
| 3 | 跨行 `0..1 × 1..3` | 高度 = 两行高 + 一个 gap |
| 4 | 跨行跨列 `0..2 × 0..2` | 双向并集 |
| 5 | 冲突（两个控件同格） | `place` 返回 `Err` 或 `debug_assert` 触发，**不 panic 于 release** |
| 6 | 内容溢出跨格区 | 依 §2.2 决策：A → 像素被裁；B → 像素越界 |
| 7 | 空 Grid（0 子控件） | 不 panic、尺寸为 0 |
| 8 | 1×1 Grid + 1 个子控件 | 占满整个内容区 |
| 9 | 自动流 + 显式混合 | 自动控件落在**第一个能放下的空位**（用 §2.3 的掩码语义验证） |

### 4.2 几何断言 vs 像素断言

**以几何断言为主**：`child_rects()` 是纯函数（输入轨道宽高 + 区间 → 输出矩形），
可以直接断言 `Rect{x,y,w,h}`，失败信息精确到数值，且不依赖字体度量。

**像素断言只在两处**：
1. 场景 6（溢出裁剪）—— 只有像素能证明"内容真的被裁掉了"；
2. 场景 9（自动流落位）—— 用彩色子控件占据格子的像素位置反推，比读内部字段更接近用户视角。

### 4.3 性能目标

| 指标 | 目标 | 依据 |
|---|---|---|
| 10k 节点 Grid 的 `measure + arrange` | **≤ 3 ms** | 现状 11k 节点全树重排 1.26ms，Grid 比 Flex 多一次轨道归因，给 2.4× 余量 |
| 冲突检测 | ≤ 0.3 ms @ 10k | O(n log n + n·rows/64) |
| 跨格控件（跨度 ≤ 3）的归因 | ≤ 0.1 ms @ 10k | 线性 |

**不达标的处理**：如果 min/max-content 两遍测量让 10k 节点超过 3ms，
退回单遍 + 0 近似，并把"Auto 轨道可能过宽"写进已知限制。

## 5. 可复用的抽象

### 5.1 区间几何（`IntervalSet`）

跨格需要的原语其实与 UI 无关：

```rust
pub struct IntervalSet { /* 排序的、不相交的 [start, end) 列表 */ }
impl IntervalSet {
    pub fn insert(&mut self, start: u32, end: u32) -> Result<(), Overlap>;  // 冲突即 Err
    pub fn first_gap(&self, len: u32) -> Option<u32>;                       // 找连续空位
    pub fn covered_len(&self) -> u32;
}
```

**可复用到**：

| 场景 | 用法 |
|---|---|
| `TreeView` 虚拟化范围 | `visible_range = 滚动区间 ∩ 总行区间`，用 `first_gap` 反推"未渲染的行" |
| 多窗口语义合并 | 每个窗口的"已暴露节点区间"求并，得到去重后的 Agent 可见集 |
| 脏区合并 | 现有 `DirtyRegion` 已经是"合并相邻矩形"，一维版本可直接用它 |

### 5.2 放哪个 crate

**`IntervalSet` → `y901-core`**：它是纯数据结构，零依赖，且 `y901-core` 已被
`y901-ui` / `y901-agent` / `y901-extras` 同时依赖 —— 放这里三方都能用，不引入新边。

**约束求解（CSP）→ `y901-ui`**：它需要 `Constraints` / `Size`，属于布局语义，不该下沉到 core。

**判定标准**（写进 Guide，避免下次纠结）：*只依赖标准库 + 数值的 → core；依赖布局/渲染概念的 → 留在上层。*

| # | 问题 | 选项 | 我的倾向 |

| ① | 跨格内容溢出怎么办 | A 裁到并集 / B 允许溢出 / C 反向撑开轨道 | **A**（与现有 `children_clip` 一致、无重排） |

## 7. 实施顺序（决策后）

1. `y901-core::interval`（`IntervalSet` + 单测，零 UI 依赖）
2. `Grid::place` + 冲突检测（几何断言，9 个场景里的 1/2/3/4/5/7/8）
3. `child_rects` 的区间并集 + `children_clip` 改写（含像素断言场景 6）
4. min/max-content 归因（性能基准 + 10k 目标）
5. 自动流（场景 9）
6. 文档：`FRAMEWORK_GUIDE §40` 增补 `children_clip` 的区间语义
