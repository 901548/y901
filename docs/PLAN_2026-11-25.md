## 批次 1（P0）：X11 传输层 —— 会卡死真实用户

**为什么排第一**：`GetImage` 读回 1080p（8.3 MB）或大段剪贴板目前会让 X11 流**永久错位**
（reply length 已按 CARD32 修，但半包重组与 `bytes_after` 仍未处理）。X11 是 Tier 2
里唯一"能跑真窗口"的 Linux 后端，这条路径坏掉 = 剪贴板和大图直接不可用。

| 项 | 内容 | 文件 |
|---|---|---|
| 1.1 | `Connection` 增加 32 字节定长读 + 部分读偏移；`next_packet(0)` 返回 `Ok(None)` 而不是 `EINVAL` | `y901-backend-x11/src/conn.rs` |
| 1.2 | `get_property` 解析 `bytes_after` 并循环取全（或显式报"被截断"） | 同上 |
| 1.3 | 所有编码器统一走 `length_units(bytes) -> Result<u16>`，超限拆包或报错 | `encode.rs` |
| 1.4 | `poll_events` 出错时把 `pending` 事件放回（现在 `mem::take` 后直接丢，`WM_DELETE_WINDOW` 会丢） | `conn.rs` |

**验证**：
- 单测：用内存 pipe 模拟"半包到达 / 超长 reply / 截断属性"，断言重组正确（这需要把
  `Connection` 的 IO 抽成 `Read + Write` 泛型，或加一个 `#[cfg(test)]` 的假流）。
- 跨编译：`cargo check --workspace --target x86_64-unknown-linux-gnu --all-targets`。
- 真机：WSL `bash scripts/linux-verify.sh`（需要 `cargo fetch` 先联网一次）。
- **风险**：抽 IO 泛型会碰到 X11 代码的很多调用点；若成本过高，退化为"加重组缓冲 +
  `read_exact` 循环"，不改泛型。
