# 自研 TTF 字体引擎：全景架构与避坑指南

> 状态：**设计定稿，尚未编码**
> 前置条件：Step 1 已完成（纯 CPU 软光栅化，与 D3D11 逐像素比对 `max_diff = 2`）
> 目标：用 `ttf-parser` + 自研光栅化，替换 `TextEngine`（DirectWrite），**`y901-widgets` 一行不改**。

---

## 0. 先立三条铁律

这轮最容易翻车的不是算法，是**契约**。先把三条铁律钉死：

**铁律 1：布局度量必须逐位相同。**
`cell_span(ch)` 决定 `draw_text` 的前进宽度，前进宽度决定每个字形画在哪。只要自研引擎的
advance 与 DirectWrite 差 0.5px，整行文字就会累积偏移，所有像素比对全部失效。
→ **先对齐度量，再谈像素**。

**铁律 2：图集协议不能变。**
现有 `TextEngine` 对外只暴露 `atlas: Vec<u8>`（RGBA，`a=255`，`rgb` 存覆盖度）、
`atlas_size`、`take_dirty() -> (reset, Vec<DirtyRect>)`。
`D3dBackend::sync_atlas` 与 `SoftBackend::draw_text` 都直接读它。
→ 新引擎必须**原样实现这套协议**，否则两个后端都要改。

**铁律 3：一切都是确定性的。**
同样的 `(字体, 字号, 字形, 亚像素相位)` 必须永远光栅化出**逐字节相同**的位图。
否则快照测试、A/B 对比、回归全部失去意义。→ 禁止在光栅化里用任何依赖迭代顺序或未初始化内存的东西。

## 1. 核心算法选型与权衡

### 1.1 曲线展平（Flattening）

TrueType 的 `glyf` 只有**二次**贝塞尔；CFF/OTF 是**三次**。两套都要支持，但可以共用一套框架。

#### 二次曲线：用"平坦度测试 + 自适应细分"，不要均匀采样

二次贝塞尔 `B(t) = (1-t)²P0 + 2(1-t)t·P1 + t²P2`。

**平坦度判据**（把曲线退化成一条线段是否可接受）：

```
d = |cross(P1 - P0, P2 - P0)| / |P2 - P0|      // P1 到弦 P0P2 的垂距
若 d ≤ tol 且 |P2 - P0| < 某上限  ⇒ 直接输出线段 P0→P2
```

其中 `tol = 0.25px`（在设备像素空间，不是 font unit）。

**递推**（de Casteljau 中点分割）：

```
P01 = (P0+P1)/2,  P12 = (P1+P2)/2,  P012 = (P01+P12)/2
左半 = (P0, P01, P012)，右半 = (P012, P12, P2)
```

递归到平坦为止。**为什么不用固定段数**：
- 固定 16 段：小字号时过度细分（浪费），大字号时又不够（有棱角）；
- 自适应：直线段直接 1 段，弯曲处自然加密，段数天然随字号缩放。

**理论上界**（用于预算，不用于实现）：均匀 n 段时误差
`err ≤ |P0 - 2P1 + P2| / (8n²)`，故 `n ≥ sqrt(|P0-2P1+P2| / (8·tol))`。
15px 中文字形的一个横钩，典型 `n = 3~6`；复合曲线整字约 200~400 段。

#### 三次曲线（CFF）

同样用自适应，但平坦度要**两个控制点**都算：

```
d1 = dist(P1, line P0P3),  d2 = dist(P2, line P0P3)
若 max(d1, d2) ≤ tol ⇒ 线段
```

`P0≈P3`（退化）时改用 `max(|P0-P1|, |P2-P3|)` 做判据，否则除零。

#### 直线段绝不浪费算力

- 字形里 60~70% 的段是直线（尤其 CJK 的横竖）。**不要**给直线做任何细分；
- 长度 < 0.01px 的段直接丢弃（不产生边，省扫描线时间）；
- 相邻共线段合并（可选优化，收益约 5%，最后做）。

#### 数值格式（重要）

坐标统一用 **26.6 定点**（1 单位 = 1/64 px），与 FreeType 一致：

- 轮廓点从 font unit（如 2048/em）缩放：`px = v * size / units_per_em`，用 i64 中间量算完再转 26.6；
- 扫描线求交用 **16.16 定点**（交点 x 精度 1/65536，足够算精确覆盖面积）；
- **禁止**在光栅化里混用 f32——f32 在 x 方向累积误差会直接表现为"某一列像素偏一档"。

### 1.2 扫描线填充与非零环绕

#### 数据结构

```
EdgeList: 按 ymin 排序的边数组（每条边：x0,y0,x1,y1, dir=±1, 当前 x 与 dx/dy）
Buckets:  以扫描线为索引的"新边"桶（ymin 在这里的边入桶）
AET:      活动边表（按当前 x 排序）
```

**扫描线步进**（每条扫描线 y）：

1. 把 `Buckets[y]` 的边加入 AET；
2. 从 AET 移除 `y >= ymax` 的边（注意用**半开区间** `[ymin, ymax)`）；
3. 对 AET 按当前 x 排序（小表用插入排序，几乎有序，O(n)）；
4. 两两配对求区间，累加**带符号**环绕数（向右的边 +1，向左的边 −1）；
5. 环绕数 ≠ 0 的区间判为内部。

#### 非零环绕：为什么必须按方向计符号

`o`、`e`、`A`、`8` 这些字形有内孔。轮廓方向是**外圈顺时针、内圈逆时针**（或反之，取决于字体）。
若只用"奇偶规则"，重叠笔画（CJK 的"田"叠加部首）会被误判成空洞。
→ **非零规则**：内部 = 环绕数 ≠ 0。每个带符号边改变环绕数，重叠区域累加后仍 ≠ 0，正确。

#### 四个必须提前处理的坑

| 坑 | 症状 | 解法 |
|---|---|---|
| **顶点双计** | 扫描线正好穿过顶点时，环绕数被加两次 → 出现 1px 竖线或空洞 | 半开区间：边的 y 范围 `[ymin, ymax)`，落在 ymax 的顶点不算 |
| **水平边** | dy = 0 除零 / 被当成扫描线自身 | 直接跳过（水平边对覆盖无贡献） |
| **自相交轮廓** | CJK 偏旁偶尔自交 | 非零规则本身能正确处理，但**符号必须一致**（同一轮廓的边 dir 一致） |
| **复合字形** | `ttf-parser` 会递归展开，但带 2×2 变换与偏移 | 必须把变换矩阵应用到每个点（含缩放/镜像，镜像会翻转 dir！） |

复合字形是**最容易被忽略的错误源**：镜像变换后 `dir` 要取反，否则内孔变实心。

### 1.3 抗锯齿：选"面积累积"，不要选超采样

三种方案对比（同一字形，15px，约 300 段）：

| 方案 | 覆盖率精度 | 相对成本 | 结论 |
|---|---|---|---|
| 4× 垂直超采样 | 垂直 4 档，水平仍带锯齿 | 4× | 水平边缘会有台阶（`/` 斜杠最明显） |
| 4×4 超采样 | 16 档 | 16× | 质量够，但 CPU 成本对 CJK 不可接受 |
| **面积累积（cell + cover）** | **水平精确解析 + 垂直精确解析** | **约 1×** | **选它** |

**面积累积算法**（FreeType smooth / libart 那一套）：

对每条边，把它跨越的每个像素**格**内的贡献拆成两部分：

```
area(cell) += 该边在该格内与"格中心线"围成的带符号面积
cover(cell) += 该边在该格内的带符号"垂直长度"
```

然后**逐行前缀和**：

```
acc = 0
for x in row:  acc += cover[x];  coverage[x] = clamp(|area[x] + acc|, 0, 1)
```

它给出的是**精确的解析覆盖率**（不是采样近似），且成本只与**边数**成正比，与像素数无关——
这正是 CJK 需要的：字形 300 段、包围盒 16×18，成本 ≈ 300 次边遍历，而不是 16×18×16 次采样。

**唯一的实现难点**：每格面积/cover 的带符号计算容易写错。验证手段见 §5 M1 的验收标准
（"总墨量必须等于多边形面积"——这是一条数学恒等式，能抓出几乎所有符号错误）。

## 2. 渲染质量与对齐

### 2.1 亚像素定位：x 轴分相位，y 轴绝不分相位

**这是整个设计里最重要的取舍。**

- 文本行的 y 由布局决定，我们的行高是整数（`cell.h`），基线永远落在整数像素上
  → **y 方向不存在亚像素问题，直接不做**（否则缓存 ×4，收益几乎为零）。
- x 方向由 `draw_text` 的 pen_x 决定，`Flex` 的中点对齐会产生 `.5`、`.25` 这类偏移
  → 必须处理。

**方案：4 相位量化 + 相位进 key**

```
phase = round(frac(x) * 4) & 3      // 0, 1/4, 1/2, 3/4
光栅化时把整个轮廓平移 phase/4 像素（真的平移，不是取整）
缓存 key 包含 phase
```

**为什么不用"四舍五入到整像素"**：那会让一行里每个字的左右间距跳动 0.5px，中文尤其明显
（笔画多的字看起来"挤在一起"）。4 相位是**业界标准**（FreeType 默认 1/4 量化）。

**性能代价**：缓存条目 ×4（只在真正用到的相位上生成）。冷启动时多 4 倍光栅化，热路径无差别。

**降级策略**（图集紧张时）：只对 phase=0 做缓存，其余相位**每次现场光栅化**（成本 ≈ 30µs/字），
或直接退化为"整像素对齐"。二者都由 §3 的占用率触发。

### 2.2 Hinting：现阶段明确不做，但要做"两件半"补救

TrueType 的字节码 hinting 是**不可接受的工作量**（解释器 + 指令集 + 字体私有表）。
FreeType 的 autohinter 也是几千行。**本轮一律不做。**

但完全不管，12px 中文会明显发糊。折中做三件事：

1. **基线对齐（必须）**：`baseline_y = round(baseline_y)`。不做这一步，y 方向也会出现 1/2 像素模糊。
2. **Gamma 校正（必须）**：覆盖度 → alpha 需要幂函数。现有 GPU 路径用 `pow(cov, 1/2.2)`，
   CPU 路径必须**用同一个 gamma**，否则 A/B 对比永远对不上，用户看到的粗细也会变。
   → gamma 作为引擎参数，默认 1/2.2，可用环境变量覆盖。
3. **stem darkening（可选，后置）**：小字号时把覆盖率整体抬一点（`cov' = 1-(1-cov)^k`，k≈1.2），
   补偿"细笔画被 AA 稀释"。视觉上更像 ClearType，但会改变墨量 → **必须单独开关**，默认关闭。

**质量预期（诚实的）**：15px 无 hinting 的中文，与 DirectWrite 相比笔画会**偏软、偏灰**，
但不会出现"缺笔画"。A/B 时不要指望逐像素相似，只要求结构一致（§4.3 的判据）。

### 2.3 度量对齐（铁律 1 的落地）

| 度量 | 来源 | 要求 |
|---|---|---|
| `cell.w / cell.h` | `cell_metrics_for(size)`（已有） | **完全复用**，不自算 |
| `cell_span(ch)` | 由 advance 推出：`round(advance / cell.w)`，≥1 | 必须与 DirectWrite 的取整规则一致；差 1 会导致整行错位 |
| `ascent` | `font.ascent * size / units_per_em` | 与 DirectWrite 差 ≤0.5px（影响 bearing_y） |
| `advance` | 字形 advance | 逐字记录偏差，M1 验收要求 `|Δ| ≤ cell.w*0.05` |

> 关键：**`cell_span` 一旦不同，后面所有像素对比都不必做了**。所以 M1 的第一条测试就是
> "同一字符串，两套引擎的 `cell_span` 序列完全相同"。

## 3. 缓存与内存管理

### 3.1 图集 key 的设计

```
key = (glyph_index: u16, size_q: u8, x_phase: u8, y_phase: u8=0)
```

- `size_q`：字号量化到整数 px（我们的引擎是**单字号**，所以实际是常量）；
- `x_phase`：0..3（见 §2.1）；
- `y_phase`：恒为 0（见 §2.1）。

**为什么不做 `size` 连续值**：一旦支持多字号，量化到 1/4 px 就够；
连续 key 会让缓存命中率崩塌（每个字号都有自己的位图）。

### 3.2 容量核算（1024² 图集）

```
图集像素总数 = 1024 × 1024 = 1,048,576 px（内存 4 MiB）
15px CJK 字形 ≈ 16×18 = 288 px²，加 1px padding ⇒ 17×19 = 323 px²/槽
理论满载 = 1,048,576 / 323 ≈ 3,240 槽
按 Skyline 实际利用率 ~70% 估算 ⇒ 约 2,300 槽
```

| 场景 | 唯一字形数 | 需要槽位（4 相位） | 可用约 2,300 | 结论 |
|---|---|---|---|---|
| 英文界面 | < 100 | 400 | 17% | 轻松 |
| 中文一屏 | 800~1,500 | 3,200~6,000 | 139%~261% | **装不下** |
| 中文长文滚动 | 2,000~3,000 | 8,000~12,000 | 348%~522% | **必然驱逐** |

**结论**：1024² 对 CJK + 4 相位**远远不够**（一屏中文就打满 1.4~2.6 倍）。三个选项，按优先级：

1. **相位分层**：phase=0 单独一个小图集（512²），phase≠0 放主图集 → 冷字永远有位置；
2. **涨到 2048²**（16 MiB；同样口径约 **9,000 槽**，一屏中文 + 4 相位刚好够）——**推荐**，简单直接；
3. **按需降级**：占用率 > 85% 时，新字形一律用 phase=0。

### 3.3 LRU 驱逐：要"成本感知"，不要朴素 LRU

朴素 LRU 的问题：滚动长文时，同一批字反复进出，**每秒重光栅化上千次**（每次 30µs ⇒ 30ms/帧，直接崩）。

**两级策略**：

1. **热集固定（pin）**：最近 N=512 个被用到的字形不参与驱逐（相当于 LRU 保护带）；
2. **驱逐顺序**：
   - 先驱逐 `phase ≠ 0`（它们可以随时按需重建，且视觉损失最小）；
   - 再驱逐 `area` 最大的（省空间最多，但重建最贵 → 折中：按 `area` 降序、`last_used` 升序的加权）；
   - **绝不驱逐**：当前帧正在绘制的字形（用 `begin_frame` 的帧号做保护，协议已存在）；
3. **重建节流**：驱逐后若同一帧内又请求同一字形，先返回"空白占位"（1px 透明），
   下一帧再光栅化——避免"驱逐→立刻重建"的抖动。

**驱逐频率的量化目标**：稳态（1,000 字滚动）下 **每帧驱逐 ≤ 4 个字形**。
超出就说明图集太小，应该涨尺寸而不是优化算法。

### 3.4 两级缓存：轮廓缓存 + 位图缓存

**只缓存位图是浪费的**：同一字形在 4 个相位下重建，轮廓展平要做 4 次。

```
OutlineCache: glyph_index → Vec<Line>（已展平、已按字号缩放，26.6 定点）
              15px CJK 约 300 段 × 8 B = 2.4 KB/字
              1,000 字 ≈ 2.4 MB（可接受，LRU 上限 2,000）

BitmapCache: (glyph, phase) → atlas slot（现有 Skyline + LRU）
```

轮廓缓存命中 ⇒ 换相位重建位图只需"平移 + 光栅化"（约 15µs），比重新解析 `glyf` + 展平（约 40µs）快一倍多。

## 4. 架构集成与无缝切换

### 4.1 接口：不要发明新协议，先"抽出"现有协议

现有 `TextEngine` 的对外面（被两个后端使用）恰好是 8 个成员：

```
new(family, size, cell_w, cell_h) -> Result<Self>
glyph(&mut self, ch) -> Option<&GlyphInfo>
cell_span(&self, ch) -> u32
atlas: Vec<u8> / atlas_size: u32
take_dirty(&mut self) -> (bool, Vec<DirtyRect>)
begin_frame(&mut self)
ascent: f32 / cell_width: f32 / cell_height: f32
```

**做法**：

1. 定义 `trait FontEngine`，把这 8 个成员**原样**搬进去（`GlyphInfo` / `DirtyRect` 结构体不动）；
2. `impl FontEngine for TextEngine`（DirectWrite，零改动）；
3. `impl FontEngine for MyFontEngine`（新）；
4. `D3dBackend` / `SoftBackend` 的字段类型从 `TextEngine` 改为 `Box<dyn FontEngine>`，
   构造时按开关选择实现。

**`y901-widgets` 与 `y901-ui` 完全不需要改**——它们只通过 `RenderCtx`/`TextMetrics` 间接使用，
根本不认识 `TextEngine`。这是本轮设计的最大红利：**边界早就是对的**。

### 4.2 开关与降级

```
--font=legacy | self        （默认 legacy）
Y901_FONT=self              （环境变量，供测试注入）
```

降级原则：
- `self` 初始化失败（字体文件打不开 / `ttf-parser` 解析失败）→ **自动回退 legacy**，打一行警告，
  绝不让应用起不来；
- 运行时异常（如某字形光栅化 panic）→ 捕获后返回空白字形 + 计数，连续 100 次则整体回退。

### 4.3 逐像素对比：怎么比才公平

ClearType（DirectWrite 默认）与灰度 AA **本来就不一样**，逐像素严格相等是不可能的。
用四层判据，从强到弱：

| 层级 | 判据 | 用途 |
|---|---|---|
| L0 度量 | `cell_span` 序列**逐位相同**；`advance` 全部满足 `|Δ| ≤ 0.05·cell.w` | **硬门槛**，不过就别比像素 |
| L1 结构 | 墨迹包围盒差 ≤1px；墨量（覆盖率总和）差 ≤5% | 抓"缺笔画/多笔画" |
| L2 分布 | 逐像素差：`p95 ≤ 32/255`，`mean ≤ 8/255` | 抓"整体偏移/发虚" |
| L3 视觉 | 差异图里不得出现**连通的实心块**（>4px²） | 抓"局部整块错" |

给出差异图（diff heatmap）给人看，比任何单指标都有效。

## 5. 分步落地路线

### Milestone 1：三条曲线的正确性（不含缓存、不含亚像素）

**范围**：只渲染 `A`、`o`、`e`、`B`、`8`；单字号 15px；x/y 都对齐到整像素；无 hinting。

**任务**：
1. `ttf-parser` 接入 + `units_per_em` 缩放（26.6）；
2. 二次曲线自适应展平（含直线快速路径）；
3. 边表 + AET + 非零环绕；
4. 面积累积覆盖率。

**验收**：
- **恒等式**：所有字形 `Σ coverage == 多边形面积`（误差 < 0.5%）。
  这是抓符号错误最锋利的一把刀——面积算错 100% 说明 `dir` 反了或 `area/cover` 混了。
- `o` / `e` 必须**有孔**（中心覆盖率 = 0，且连通域计数 = 2）；
- `A` 的三角形内孔（部分字体有）正确；
- 与 DirectWrite 同字号位图：L1 全过、L2 `p95 ≤ 32`；
- 单字形光栅化耗时 **< 100 µs**（release，300 段）。

**已知风险**：`ttf-parser` 的复合字形变换（镜像后 `dir` 要取反）。

### Milestone 2：图集 + LRU + 协议对接

**范围**：ASCII 全集 + 动态字号；接入 `take_dirty` 协议；`--font=self` 跑通完整应用。

**任务**：
1. 轮廓缓存（`Vec<Line>`）；
2. 位图入图集（复用现有 `SkylinePacker`，1px padding）；
3. `take_dirty` 输出脏矩形（reset 标志 + rect 列表）；
4. LRU（热集 pin + 相位优先驱逐）；
5. `FontEngine` trait 抽出 + 两个后端改用 `Box<dyn FontEngine>`。

**验收**：
- **`--font=self` 下现有 508 个测试全绿**（这是"没破坏任何东西"的硬证据）；
- 应用在 `--font=self` 下启动、滚屏、输入文本均正常；
- ASCII 全图集后占用率 **< 60%**；
- 稳态滚动 1,000 字：每帧驱逐 ≤ 4 字形（§3.3）；
- 重建路径：强制 `atlas.clear()` 后所有字形能恢复（无空白格残留）。

**已知风险**：`take_dirty` 的 reset 语义必须与 DirectWrite 路径一致（否则 GPU 图集不同步 → 花屏）。

### Milestone 3：亚像素 + CJK

**范围**：x 相位 0..3；CJK 500 常用字 + 标点；图集涨到 2048²。

**任务**：
1. 相位量化 + 轮廓平移 + key 扩展；
2. CJK 复合字形（`ttf-parser` 递归展开，注意 `locl`/`vert` 表暂不支持）；
3. 图集扩容 + 占用率触发降级（>85% → 只缓存 phase 0）；
4. gamma 参数化（默认 1/2.2，与 GPU 一致）。

**验收**：
- 中文一屏（约 1,200 字）首帧建立时间 **< 60 ms**（可接受，之后全部命中）；
- 稳态帧（滚屏）**不新增光栅化**（命中率 > 99%）；
- L1 全过，L2 `p95 ≤ 40`（中文笔画密，放宽阈值）；
- 同一字形 4 个相位的位图**互相不同**（否则相位没生效）；
- 相位切换时文本不出现"左右跳动"（用相邻字符间距的方差衡量，< 0.05px）。

**已知风险**：CJK 一节 8,000 槽位的容量临界（见 §3.2）——可能真的要上 2048² 或相位分层。

### Milestone 4（可选，后置）：质量增强

- 垂直 hinting（只对齐横笔画，不做字节码）；
- stem darkening 开关；
- 多字体回退（缺字 → 下一字体）；
- 字距调整（`kern`）——注意：**会改变 advance**，必须与 `cell_span` 的整数格模型兼容，
  大概率要放弃（我们的文本模型是等宽格）。

## 6. 深坑清单（按"会死人的程度"排序）

| # | 坑 | 症状 | 根因 | 解法 |
|---|---|---|---|---|
| 1 | **advance 不一致** | 整行文字累积偏移 | 取整规则不同 | 复用 `cell_metrics_for`，`cell_span` 逐位比对（L0） |
| 2 | **非零环绕方向反了** | `o`/`e` 变实心，CJK 部首被填 | 复合字形镜像后 `dir` 未取反 | 面积恒等式 + 连通域计数双检 |
| 3 | **顶点双计** | 1px 竖线 / 局部空洞 | 扫描线正好过顶点 | 半开区间 `[ymin, ymax)` |
| 4 | **面积/cover 混淆** | 边缘灰得离谱、整块偏暗 | `|area+cover|` 用错符号或顺序 | 面积恒等式 |
| 5 | **图集 key 漏相位** | 文字左右抖动 | key 少了 `x_phase` | key = (glyph, size, phase) |
| 6 | **驱逐抖动** | 滚屏时 CPU 100%、掉帧 | 朴素 LRU 反复重建 | 热集 pin + 相位优先（§3.3） |
| 7 | **gamma 不一致** | CPU 与 GPU 粗细不同 | GPU 用 1/2.2，CPU 用线性 | gamma 参数化，两侧同一个值 |
| 8 | **图集 padding 缺失** | 字形边缘串色/发黑 | 相邻位图线性采样溢出 | 1px padding（现有 1px，保持） |
| 9 | **f32 累积误差** | 某列像素偏一档 | 坐标用 f32 | 26.6 定点 |
| 10 | **`ttf-parser` 生命周期** | 编译不过 / UB | `Face` 借用字体字节 | 字体字节常驻（`Vec<u8>` 存引擎里），`Face` 每次临时构造 |
| 11 | **空字形（空格/零宽）** | 图集塞入 0×0 槽 | 未检查 `width==0` | 直接返回空 `GlyphInfo` |
| 12 | **缺字（.notdef）** | 显示成方块 | 字体无该字 | 回退到 `.notdef`，M3 后再做多字体 |
| 13 | **CJK 部首自交** | 局部实心/空洞 | 非零规则下符号不一致 | 每个轮廓统一 dir，面积恒等式兜底 |
| 14 | **驱逐与绘制竞争** | 花屏/黑块 | 驱逐了本帧正在用的槽 | `begin_frame` 帧号保护 |
| 15 | **`take_dirty` reset 语义** | GPU 图集不同步 | reset 时未整张上传 | 与 legacy 路径逐字段对齐 |

## 8. 一句话总结

> **先把"度量 + 图集协议"对齐（M1/M2），再谈质量（M3）。**
> 算法上只有两个真正的决定：**自适应展平 + 面积累积光栅化**；
> 工程上只有一个真正的风险：**LRU 驱逐抖动**（图集容量算错会在滚屏时直接暴露）。
> Hinting 明确不做——接受"软一点的灰度"，换 3 天工期。

### 9.2 已知限制 #1：图集容量 < 工作集 × 2 时 LRU 会崩溃

**现象**（实测，512² 图集 + 1200 字工作集）：

```
建立 1200 字：23.7ms，驱逐 452，单帧最坏 8
3 轮重请求：76.4ms，驱逐 365，单帧最坏 1
建立后缓存字形数：**11**（工作集 1200）
```

每次 insert 失败要逐个驱逐才能腾出位置，而驱逐掉的又是下一帧要用的 → 缓存被冲坏。

**生产配置（2048²）不受影响**：1200字×4相位 = 4800 槽，占用 **31.7%**，驱逐 **0**，
余量 **3 倍**。

**年后要支持更小图集时的两条路**：
1. **相位分层**：phase 0 放小图集（512²），phase≠0 放主图集 → 冷字永远有位置；
2. **容量降级**：占用 > 85% 时，新字形一律只用 phase 0（C 方案的极端形式）。

另：这个坑曾经表现为“**字形被青默丢弃**”——驱逐条件写成“占用率 > 85%”，
而 Skyline 碎片化时占用率可能远低于 85% 但仍无法 insert → 一个都不驱逐 → 返回 None。
**现已修正**为“逐个驱逐 + 重试”（最多 64 次）。

### 9.3 已知限制 #2：L2（逐像素）缺少合格参照物

实测（最佳平移后）：p95 **119~255**，mean **39~69**。

**原因不是"形状算错"**：DirectWrite 默认开 **hinting**，把竖笔对齐到整像素、
非均匀移动边缘；我们是纯灰度 AA、无 hinting。两边画的本来就不是同一个形状。

**要么开启 L2 断言，需要**：
- FreeType 关掉 hinting（`FT_LOAD_NO_HINTING`）渲染同一批字形作为参照；
- 当前环境没有 FreeType（无网络、无 C 工具链）。

**在拿到参照之前，正确性由以下三条保证**（都已实测）：
1. **面积恒等式**：墨量 == 多边形面积（误差 < 0.5%）；
2. **L1 结构**：包围盒差 ≤ 2px、墨量差 0.8%~3.4%；
3. **镂空正确性**：口/日/田/回/国 的内孔数与几何推导完全一致。
